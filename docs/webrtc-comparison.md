# 통신 방식 비교: WebSocket vs SSE vs Long Polling vs WebRTC

| 기준 | **WebSocket (채택)** | SSE | Long Polling | WebRTC DataChannel |
|---|---|---|---|---|
| 방향 | 양방향 | 서버→클라이언트 단방향 (송신은 별도 HTTP) | 요청/응답 반복 | 양방향 P2P |
| 지연 | 낮음 (프레임 오버헤드 2~14B) | 낮음 | 요청당 RTT + 헤더 | 가장 낮음 (직접 연결 시) |
| 서버 경유 | 항상 | 항상 | 항상 | 직접 연결 시 경유 안 함 (TURN 사용 시 경유) |
| **서버가 메시지를 보는가** | 예 | 예 | 예 | **아니오** (P2P) |
| 순서/신뢰성 | TCP (순서 보장) | TCP | TCP | SCTP: 순서/신뢰성 선택 가능 |
| 재연결/이어받기 | 직접 구현 (본 과제: `lastSeq`) | `Last-Event-ID` 표준 내장 | 쉬움 | ICE 재협상 필요, 복잡 |
| 인프라 | LB의 Upgrade 지원, 장기 연결 | 일반 HTTP | 일반 HTTP | 시그널링 서버 + STUN + TURN |
| 방화벽/프록시 | 대부분 통과 (443) | 매우 잘 통과 | 매우 잘 통과 | UDP 차단 환경에서는 TURN(TCP/443) 필요 |
| 확장 시 부담 | 연결 수 × 메모리 | 연결 수 × 메모리, HTTP/1.1 도메인당 6연결 제한 | 요청 폭증 | 미디어/데이터는 서버 부담 없음, 시그널링만 |

## 이 과제에서 WebSocket을 택한 이유

이 서비스의 핵심 요구는 **서버가 모든 이벤트를 받아 원장에 기록하는 것**이다. 서버가 seq를 발급하고 중복을 거르며, 나중에 상태를 복원해야 한다.

- **WebRTC DataChannel은 요구사항과 정면으로 충돌한다.** P2P에서는 메시지가 서버를 거치지 않는다. 그러면 서버 seq 발급, 멱등성 검사, 이벤트 원장, 시점 복원이 모두 불가능하다. 두 클라이언트가 각자 서버에도 보내게 만들 수는 있지만, 그러면 "P2P로 받은 메시지"와 "서버 원장"의 순서와 내용이 어긋나는 이중 진실 문제가 생긴다.
- **SSE + HTTP POST**도 충분히 가능한 대안이다. 송신은 이미 `POST /sessions/{id}/events`로 제공한다. 수신은 SSE의 `Last-Event-ID`에 seq를 넣으면 resume이 표준으로 해결된다. 프록시 친화성이 중요한 환경(기업망)이라면 대체 전송으로 추가할 만하다. 다만 typing처럼 잦은 상향 신호마다 HTTP 요청이 생기고, ack 상관관계도 요청/응답으로 나뉘어 WebSocket을 1차 채널로 택했다.
- **Long Polling**은 연결 유지가 불가능한 환경의 마지막 대비책이다.

## WebRTC가 맞는 경우와 공존 구조

1:1 서비스에 **음성/영상 통화**가 추가된다면 WebRTC가 맞다. 미디어는 지연이 중요하고, 서버가 내용을 기록할 필요가 없으며, 대역폭 비용을 서버가 질 이유도 없기 때문이다. 이때 이 시스템의 역할은 다음과 같다.

```
WebSocket (기존)  : 채팅 이벤트 + WebRTC 시그널링(offer/answer/ICE candidate) 중계
WebRTC            : 음성/영상 미디어 (P2P, 실패 시 TURN)
이벤트 원장        : CALL_STARTED / CALL_ENDED 같은 "통화 메타 이벤트"만 기록 → 시점 복원에 "통화 중" 상태 포함 가능
```

- 시그널링 메시지(SDP, ICE)는 휘발성이라 TYPING처럼 **저장하지 않고 중계만** 한다.
- 통화 시작/종료처럼 상태를 바꾸는 사건만 원장 이벤트로 남겨 복원 대상에 포함한다.
- 운영에서 고려할 점: TURN 서버(coturn) 비용과 대역폭, NAT 통과 실패율 모니터링. 3명 이상으로 확장하면 SFU(mediasoup, LiveKit)가 필요하다.
